# Fable's note to Opus: building the maps, 2-fers and resources quicker and more accurately
(Fable, Oct 29 2026 ~10:40 PM, written at Brandon's ask. Everything here comes from what actually went wrong or worked today. Nothing here changes Rule G; it is how to RUN it well. Every chat should skim this once.)

## Where the time really goes
A park is cheap when a LAYER answers it and expensive when a PERSON reads a page. So the whole game is: move work from pages to layers, from one-at-a-time to batches, and never do the same look-up twice.

## The twelve habits
1. **Saved copies first, network last.** We lost an hour today because a chat read a stale copy of the key, and nearly lost more re-fetching water we already had. Before any fetch, ask: do we already hold this (saved water tiles, parcel copies, the one-time Recreation.gov pull, yesterday's layer read)? The answer file you need usually exists. And always read the LIVE key in KPC-Links, not the once-a-day KPC-Data copy.
2. **IDs beat names; names need a per-agency word list.** The best join is the agency's own ID (FWS tract id, RIDB id, NB zone number, Recreation.gov id in a BLM polygon): it works at any distance and never argues about spelling. Names are the fallback, and then only with that agency's type words stripped (BLM's RMA/SRMA/HMA list, the EN/FR map in Canada). Chasing name matches one by one is the slowest thing we do: collect the pattern, add it to the word list, rebuild once.
3. **Polygons before pages (P-2).** One point-in-polygon pass per state against every layer we hold answers hundreds of parks in minutes and tells you exactly which parks still need a human. Today that turned 566 'look it up' jobs into ~150 real page reads. Never open a web page for a park a layer can answer.
4. **Batch by agency and by county, never by park (P-3/P-4).** 30 Oklahoma historic sites = one layer probe. 293 parcel parks = 229 county requests, and a statewide parcel layer collapses a whole state into one. If you are about to file 20 similar requests, stop and find the one request that answers all 20.
5. **One book, one row, one 'why not'.** Everything found goes in the Fable file row (source, rule step, result, tag) the moment it is found. The why-not tag is the to-do list: it sorts the leftovers by cure (no-layer -> Source Book; needs-parcel -> county batch; name-mismatch -> word list / website name; picture-map-only -> stays a pin). If a row is right, nobody ever searches that park again - that is the whole point.
6. **Fix data at the source and sanity-check with arithmetic.** The size-unit bug poisoned R-G8 and the sweep because stored 'acres' were not acres. Convert at the source once, then check stored value vs computed value (acres vs the polygon's own area) and flag 10x gaps. A number a bot can verify should never be trusted un-verified.
7. **Independent eyes, small samples, known answers.** The builder never grades its own work: chat 11 checks 30, not 300 - a clean 30 with known answers (KY 19/19) catches what matters. And when the checker can't SEE (no map), its yes is only a guess: give it screenshots or a layer probe, or record NOT SURE honestly.
8. **Save as you go.** The 557-park lake run died at its 4-hour limit holding everything in memory - total loss. Every long job saves per state/chunk; every big run is split so a failure costs minutes, not hours. Same reason the 2-fer areas are now 1/3 size.
9. **Quarantine, never delete; stage, never ship.** Old-key results are marked 'rerun needed' and kept for comparison until the new run passes. New work is staged for the dump. Deleting early destroys the comparison that catches the next bug; shipping early puts bugs on the site. (Pins never move; parks are never 'cleaned up' - R0.)
10. **Keep bulk out of the website repo.** Throwaway data (look-up answers, screenshots, probe dumps) lives in KPC-Data on a branch that can be wiped; small JPEGs, deleted after use. The website repo got to 687 MB because we forgot this for four hours.
11. **Write the ruling, then never re-ask.** Every Brandon ruling gets a dated line in the notes (R-G7, R-G8, POTA plain answers...). Half of 'thinking' is re-deciding things already decided; the notes are cheaper than the debate. A new situation = a numbered grey area to HQ, never a guess, and never a quiet new rule.
12. **The look-up bot is the hands; keep it fed and keep it honest.** Anything a chat cannot open goes to the bot in a batched request, jobs run side by side, and the asking chat marks answers 'read' so they get deleted. But drop junk early: an ArcGIS-Online keyword search returns mostly private hobby layers - official hosts only (RESEARCH ORDER: state portal, then agency, then search).

## The order that works (per state or province)
our saved docs -> the agency's own layers (IDs, then names with the word list) -> point-in-polygon pass -> county parcels by address -> page reads for the few left -> picture-map links recorded, not traced -> tag what remains. Then the 2-fer line runs the state, chat 8 grades, chat 11 checks, and the state never comes back.

## What NOT to optimize
Accuracy rules are not the bottleneck and are not negotiable: official sources only, R-G8's kind-of-place test, the private-land cuts, the notices, chat 11's independent check. Every shortcut above saves time BEFORE the rules, never around them.
